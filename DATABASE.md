# Database: PostgreSQL + Drizzle + Docker

This is the reference for anyone (developer or agent) working on the `tic-api` database.
Read it before changing the schema or deploying.

## Stack

| Piece | What | Where |
|---|---|---|
| Database | PostgreSQL 17 (`postgres:17-alpine`) | `docker-compose.yml` |
| ORM | `drizzle-orm` using the **`bun-sql`** driver (Bun's built-in `Bun.SQL`) | `src/db/index.ts` |
| Schema | TypeScript tables, the only source of truth | `src/db/schema.ts` |
| Enum values + JSON shapes | `as const` arrays and spec §5 types (Plan, Route…) | `src/db/types.ts` |
| JSON columns | Custom `jsonb` type that works with Bun.SQL | `src/db/jsonb.ts` |
| Demo data | Spec's 4 demo invoices, users, settings | `src/db/seed.ts` |
| Migrations | SQL files generated by `drizzle-kit` and **committed to git** | `drizzle/` |
| Migration runner | Bun script using `drizzle-orm/bun-sql/migrator` | `src/db/migrate.ts` |
| Tooling config | `drizzle-kit` config | `drizzle.config.ts` |

> `postgres` (postgres.js) is a **devDependency used only by drizzle-kit** (`db:push`, `db:studio`),
> because drizzle-kit can't use Bun's built-in client. App code must use `db` from `src/db`.
> Never import `postgres` or `pg` yourself.

## Tests that use the database

`test/payouts.test.ts` runs the authenticated payout workflow over HTTP against PostgreSQL in a newly created workspace. `test/auth.test.ts` covers accounts, sessions, invitations, workspace isolation and read-only MCP/API keys. Both require a dedicated local `*_test` database. One-time setup:

```sh
docker compose exec db psql -U tic -d postgres -c "CREATE DATABASE tic_test"
DATABASE_URL=postgres://tic:tic@localhost:5432/tic_test bun run db:migrate
```

Use `bun run test`, `bun run test:workflow`, or `bun run test:auth`. The runner overrides `DATABASE_URL` in separate test processes before database modules initialize, even when the application uses a remote database. `TEST_AUTH_DATABASE_URL` optionally selects a different local test database for auth tests. Without test URLs, `bun run test` runs only unit tests. The reset integration test is excluded unless explicitly requested with `--include-reset`.

## Environment variables

Copy `.env.example` to `.env`. Bun loads `.env` automatically, so you don't need `dotenv`. Never commit `.env`.

| Variable | Used by | Default |
|---|---|---|
| `DATABASE_URL` | app, migrations, drizzle-kit | `postgres://tic:tic@localhost:5432/tic` |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | Docker container | `tic` / `tic` / `tic` |
| `POSTGRES_PORT` | host port the container is published on | `5432` |

If you change the `POSTGRES_*` values, update `DATABASE_URL` to match.

## Local development

Requirements: Bun and Docker with the **Compose v2 plugin** (`docker compose version` must work).

```sh
bun install
cp .env.example .env        # first time only
bun run db:up               # start Postgres and wait until it is healthy
bun run db:migrate          # apply migrations in drizzle/
bun run db:seed             # load the 4 demo invoices, users and settings
bun run dev                 # start the API
```

### Scripts

| Script | What it does |
|---|---|
| `db:up` | Start the Postgres container in the background and wait for its healthcheck |
| `db:down` | Stop the container. **Data is kept** in the `tic-db-data` volume |
| `db:reset` | **Delete all data**, recreate the container, re-run migrations and seed |
| `db:logs` | Follow Postgres logs |
| `db:psql` | Open a `psql` shell inside the container |
| `db:generate` | Diff `schema.ts` against the last snapshot and write a new SQL migration to `drizzle/` |
| `db:migrate` | Apply pending migrations to `DATABASE_URL` (safe to re-run) |
| `db:seed` | Reset to the demo state: wipes every table **except `extraction_cache`**, then inserts the demo data. Refuses non-local DBs unless `SEED_ALLOW_REMOTE=1` |
| `db:push` | Push `schema.ts` straight to the DB with no migration file. **Local prototyping only** |
| `db:studio` | Open Drizzle Studio (web UI to browse data) |

## Schema overview (Corredor)

The product spec is `Corredor Spec.html` (Architecture §5 types, §11 data model).
**Postgres records what happened.** Reference data (the `rules.json` rules pack,
`offramps.json`, `fx.json`, the OFAC SDN list) stays in versioned files in git
so the rules engine is deterministic. Plans store `rules_version` plus a route
snapshot, so history stays readable after those files change.

```
users ─────────────┐ (approvers, reviewers, audit actors)
invoices 1──1 payouts ──┬─< screenings        OFAC result + human review
                        ├─< plans ──< memos   one plan per rules-engine run (slider moves add rows)
                        ├─< vendor_requests   P1 "missing info" email drafts
                        ├─< approvals         first / second approver, linked to the plan they saw
                        ├─< payments ──1 reconciliations
                        │            └─1 journal_entries ──< journal_lines
                        └─< audit_events      append-only hash chain (payout_id null = global event)
extraction_cache  PDF sha256 → extracted invoice (survives db:seed)
settings          key/value: policy, demo_as_of, rules_version
```

| Table | Purpose | Notes |
|---|---|---|
| `invoices` | Extracted invoice fields (editable) | `raw_extraction` keeps the untouched model output. `low_confidence` lists field names to highlight |
| `payouts` | Unit of work: planned → approved → paid → booked | `status`, `as_of`, `amount_usd`, `recommended_route_id`, `has_warnings` are copied from the **latest plan** for the inbox. Update them whenever you insert a plan |
| `screenings` | OFAC fuzzy match | `possible_match`/`hit` block until `review_decision` is set |
| `plans` | Every engine run | Latest per payout = `ORDER BY created_at DESC LIMIT 1`. `plan` is the full engine output. `plan_hash` = sha256 of canonical plan JSON |
| `memos` | Claude/template explanation of a plan | Reuse a memo when `plan_hash` matches instead of calling Claude again |
| `approvals` | Approve/reject | Unique `(payout_id, role)` and `(payout_id, approver_id)`, so a second approver must be a different person. `amount_usd` is used for the daily cap |
| `payments` | `RailAdapter.send()` result | At most one non-`failed` payment per payout. `route` is a snapshot |
| `reconciliations` | invoice ↔ tx hash ↔ rail ref | `exception` needs a `reason` |
| `journal_entries` / `journal_lines` | Double-entry booking (USD) | A line is debit **or** credit (CHECK). The app must keep each entry balanced |
| `audit_events` | Keyed hash chain (HMAC-SHA-512) | `seq` is an identity, read before insert because it is part of the MAC (`appendAudit` in `src/services/audit-log.ts`). The columns `prev_hash` / `hash` hold the previous MAC / MAC. `key_id` supports rotation. UPDATE/DELETE are rejected by a trigger (migration 0002). `created_at` has ms precision: set it in code before MAC'ing |
| `audit_checkpoints` | Ed25519 signatures over the head MAC | Written every 10 events and when a payout is booked. Auditors verify them with the public key alone |
| `settings` | Config | `policy` = `{ secondApproverAboveUsd: 50000, dailyCapUsd: 150000 }` |

Conventions: uuid PKs, snake_case columns, `timestamptz`, business dates as
`YYYY-MM-DD` strings (`date` mode string), money as `numeric(18,2)` and FX
rates as `numeric(18,8)`, both returned as JS numbers. Enum values come from
`src/db/types.ts`.

### Gotcha: JSON columns

Always use `jsonb` from `./jsonb`, **never** `jsonb` from `drizzle-orm/pg-core`.
Drizzle's version JSON-encodes values and Bun.SQL encodes them again, so objects
get stored as JSON strings. They still read back fine in JS, but every SQL
`->`/`->>` query returns null. Example: `payload: jsonb<MyType>("payload").notNull()`.

## Using the database in code

```ts
import { desc, eq } from "drizzle-orm";
import { db, schema } from "./db";

// Inbox: payouts with invoice and latest plan
const rows = await db.query.payouts.findMany({
  with: { invoice: true, plans: { orderBy: [desc(schema.plans.createdAt)], limit: 1 } },
});

// Status change
await db.update(schema.payouts).set({ status: "approved" }).where(eq(schema.payouts.id, id));
```

Import `db` from `src/db`. Don't create new connections. `src/db/index.ts` throws at startup if `DATABASE_URL` is missing.

## Changing the schema (required workflow)

1. Edit `src/db/schema.ts`. Export every table from this file so drizzle-kit and `db.query` can see it.
2. `bun run db:generate`. Review the generated SQL in `drizzle/` (renames can come out as drop + create).
3. `bun run db:migrate` to apply it locally.
4. Commit `schema.ts` **and** the whole `drizzle/` folder (including `drizzle/meta/`) in the same commit.

Rules:
- **Never edit or delete a migration that has been merged or deployed.** Write a new one instead.
- Don't hand-edit `drizzle/meta/*`.
- Adding an enum value: add it to the array in `src/db/types.ts`, then `db:generate`.
- drizzle-kit can't change a column type when the data can't be cast (e.g. `serial` to `uuid`). Edit the **new, unapplied** SQL file by hand (see `0001`). For DB objects drizzle doesn't model (triggers, functions), use `bunx drizzle-kit generate --custom --name <name>` (see `0002`).
- If two branches both generate a migration, the second to merge must delete its own new migration, rebase, and run `db:generate` again.
- Use `db:push` only on your local DB. Never use it against shared or production databases.

## Deploying

The app needs only `DATABASE_URL`. A deploy is always: **apply migrations, then start or restart the app.**

### Option A: managed Postgres (recommended)

Neon, Supabase, Railway, Render, RDS and similar.

1. Create a Postgres 15+ database and copy its connection string.
2. Set `DATABASE_URL` in the hosting platform's secrets. Add `?sslmode=require` if the provider requires TLS (most do).
3. Run migrations as a release / pre-deploy step:
   ```sh
   bun install --frozen-lockfile
   bun run db:migrate
   ```
New accounts create their own workspace and fictional invoices. Do not run `db:seed` or enable remote seeding as part of deployment.
4. Start the app: `bun run src/index.ts`.

You don't need Docker in this setup.

### Option B: self-hosted on a VM using this compose file

```sh
git clone <repo> && cd tic-api
bun install --frozen-lockfile
cp .env.example .env
# edit .env: set a strong POSTGRES_PASSWORD and update DATABASE_URL to match
docker compose up -d --wait db
bun run db:migrate
bun run src/index.ts        # run under systemd/pm2/etc. in practice
```

Production hardening for Option B:
- **Don't expose 5432 to the internet.** Change the port mapping to `"127.0.0.1:${POSTGRES_PORT:-5432}:5432"`, or remove `ports:` if the app runs in the same compose network.
- Use a strong, unique `POSTGRES_PASSWORD`. The password only applies when the volume is **first created**. Changing it later requires `ALTER USER` in `psql`.
- Back up regularly:
  ```sh
  docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup.sql
  # restore:
  docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < backup.sql
  ```
- `docker compose down -v` / `db:reset` **deletes the data volume**. Never run them in production.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `DATABASE_URL is not set` | `cp .env.example .env` (run commands from the `tic-api/` directory) |
| `docker: unknown command: docker compose` or `unknown shorthand flag: 'd' in -d` | The Docker Compose plugin is missing. With sudo: `sudo apt install docker-compose-v2`. Without sudo: download `docker-compose-linux-x86_64` from https://github.com/docker/compose/releases, check it against its `.sha256`, and install it to `~/.docker/cli-plugins/docker-compose` with `chmod +x`. Confirm with `docker compose version` |
| `port is already allocated` on 5432 | Set `POSTGRES_PORT=5433` in `.env` and change the port in `DATABASE_URL` |
| `password authentication failed` | The volume was created with different credentials. Run `bun run db:reset` locally (wipes data) |
| `relation "..." does not exist` | Run `bun run db:migrate` |
| `audit_events is append-only` | Intended. Write a new event instead. Tamper tests: `ALTER TABLE audit_events DISABLE TRIGGER audit_events_append_only` |
| `jsonb_typeof(...)` is `string` / `->` returns null | The column uses drizzle's built-in jsonb. Switch it to `./jsonb` and re-save the rows |
| `duplicate key ... approvals_payout_approver_uq` | Same person tried to approve twice. The second approver must be someone else |
| drizzle-kit `Please install either 'pg' or 'postgres'` | Run `bun install`. `postgres` is a devDependency used by drizzle-kit |
